## Repository made public — November 12

The owner made the repository public. An audit of every tracked file and all 11 commits found one kind of personal detail: links in nine Markdown files used absolute home-folder paths that revealed the Mac account name. No email addresses (commits use GitHub's no-reply address), keys, certificates, screenshots, receipts or credentials were ever committed, and no files had been deleted from history. The links are now repository-relative, `verify.py` rejects home-folder paths and non-no-reply emails in tracked files, and, at the owner's request, history was rewritten so earlier commits no longer contain the path. The repository had no forks at the time. GitHub may still serve old commits by their exact identifier from caches until they are garbage-collected; removing those entirely requires a request to GitHub Support. Descriptive setup details (hardware, apps and calendars used, feature decisions) were kept by the owner's choice.

The user asked for album artwork, which was off in M3 by their earlier choice. It is now a separate "Show album artwork" switch under Spotify, off by default, and is the app's first network use. With it on, Personal Island asks Spotify (by Apple Event, as for the other track details) for the current track's identifier and cover URL, accepts only https URLs on i.scdn.co, and downloads the image once per track with an ephemeral session: no cookies, credentials, disk cache or redirects, a 15-second limit, image types only and at most 2 MB. The image stays in memory and is dropped when the track changes or Spotify, artwork or the app stops. Spotify's image server sees the request (the Mac's IP address and which cover). The user reported the battery icon and album artwork work. Not itemized: podcasts, local files and tracks without a cover show a placeholder.

## M3 Calendar — November 12

Version 0.6.0 (10) rebuilds with the local signing identity and passes all 241 automated tests plus Release bundle/signature checks, with no compiler warnings in app sources. GitHub's Xcode 16.4 check passed for 0.5.0.

Calendar is off by default. Turning on "Calendar in the island" adds a Calendar tab to the open island: the ongoing or next timed event (with Join for a validated https meeting link) and today's agenda with all-day events first, each with its calendar's color. Clicking an event opens it in Apple Calendar. Settings lists the calendars on this Mac so individual ones can be hidden; hidden calendars are never queried, and calendars added later appear by default. Events are read through EventKit only; the app never saves, edits or deletes events and never touches reminders. Event titles stay in memory; notes and location are read in memory only to find a meeting link and are neither shown nor stored. The agenda refreshes on calendar database changes, day and time-zone changes, wake, and at the next event start/end or midnight; turning the switch off removes all observers, cancels the timer, releases the event store and clears events.

Build-policy change, reviewed: the hardened runtime requires `com.apple.security.personal-information.calendars` to read events, and macOS 14+ requires `NSCalendarsFullAccessUsageDescription`. Apple offers no read-only option, so the permission text states that events are only read. The policy requires exactly these two entitlements and two texts; write-only calendar and reminders permissions stay forbidden.

The user reported Calendar works and asked for the next event to be shown when a day has no events. Previously an empty day showed only a timed event within 7 days. The tab now always shows a Today section ("No events" when empty) and, once nothing is left today, a Next event section with its day (for example "Tomorrow · 9:00 AM" or "Fri, Nov 20 · All day"), including all-day events, looking 30 days ahead. The user then reported this works. Not itemized by the user: agenda accuracy (all-day, ongoing, multi-day, recurring and synced Google/Outlook calendars), Join links, opening in Calendar, hiding calendars, and refresh at boundaries, midnight and wake. The lock-screen privacy rule for calendar text belongs with the lock-screen work in M4.

## M3 Spotify and remembered settings — November 12

Version 0.5.0 (9) rebuilds with the local signing identity and passes all 222 automated tests plus Release bundle/signature checks, with no compiler warnings in app sources. The user chose Spotify first, remembered settings, and no artwork for now.

Settings (islands shown, hover, capture shortcut, per-display switches, Spotify) are now stored as one small JSON value in the app's own preferences; damaged or unknown values fall back to defaults. No captures, track names or other personal content are stored.

Spotify is off by default. Turning it on (Settings → "Spotify in the island") starts observing Spotify's own playback notification and Spotify launch/quit, and adds a Media tab to the open island with title, artist/album, an extrapolated progress bar (redrawn once a second only while visible) and previous/play-pause/next. Reads and controls use Apple Events sent only to Spotify, using codes from its scripting dictionary, with two-second timeouts on a background queue; the feature never launches Spotify (an explicit "Open Spotify" button does). macOS asks once for Automation permission to control Spotify; denial is shown with a link to the settings pane, and track text still appears from the notification. Turning the switch off removes all observers, ignores late replies and clears the track. Nothing is sent online and no artwork is downloaded.

Build-policy change, reviewed: the hardened runtime requires the `com.apple.security.automation.apple-events` entitlement and an `NSAppleEventsUsageDescription` to send Apple Events. The policy now requires exactly that entitlement (true, boolean) and exactly the reviewed permission text, and still rejects every other entitlement and usage description. The local re-sign step now passes the entitlements file; without that, re-signing would have silently dropped it.

Duration units: Spotify's dictionary says seconds but Spotify reports milliseconds (matching its notification); the app treats both as milliseconds. The user should confirm the progress bar and total time match Spotify. The first user run showed no Automation prompt, so controls never worked: the permission check used wildcard event codes, for which macOS reports that consent is needed but never asks. Changing to a specific event did not help: the user still saw no prompt and no Automation entry, and macOS's privacy log showed no request from the app. A diagnostic outside the app (with asking disabled, so no prompt could appear) showed that `AEDeterminePermissionToAutomateTarget` blocked indefinitely on this Mac, so the app's request never reached the privacy service. The call is removed. Permission is now probed by sending the real player-state read: with "never interact" to check quietly, or normally with a long timeout when the user presses a control, which is what shows the dialog. Every Spotify call runs under a hard deadline (regression-tested with a call that never returns), so a stalled system service cannot freeze the feature again. The user still saw no prompt. A one-second stack sample of the running app showed its Apple Event sends blocked inside `AESendMessage`, waiting for a system reply, with one blocked thread per press. Unified logs are not readable from the development shell, so whether the privacy service received the requests could not be established. The dialog server had been running for about 15 days; a stuck or hidden earlier consent dialog is the leading hypothesis, to be tested by the user (look for a hidden dialog, otherwise restart). The app now allows only one permission request at a time, so repeated presses cannot pile up blocked requests. After the user cleared the stuck system state, the Automation prompt appeared and control worked (user report). The user then reported glitchy play/pause animation and a progress bar that could not be dragged. Cause: the app re-read Spotify immediately after a command and briefly got the old state back, flipping the icon twice, and the progress view was rebuilt on every play-state change. The app now shows the expected result immediately, waits 700 ms before confirming, ignores confirmations from superseded commands, and keeps the progress view stable. The progress bar is now a scrubber that seeks through Spotify's writable player position (time units confirmed by the user's earlier run). The user then reported that it works, covering play/pause and the draggable slider. Not itemized: quit/relaunch, denial/revocation, and whether a hover-opened island stays open while dragging off its edge. Both-display synchronization awaits the Dell. Calendar is next in M3.

## Readable export names — November 12

Dragged screenshots are now exported as `Screenshot YYYY-MM-DD at HH.MM.SS.png` using the capture time in the Mac's time zone, with ` (2)`, ` (3)`… for captures in the same second, instead of `<uuid>.png`. ## Stable local signing — November 12

Each ad-hoc rebuild changed the app's code hash, which is what macOS used to identify it, so the Screen Recording grant silently stopped applying after the 0.3.0 rebuild (user report and screenshot). The user created a self-signed "Personal Island Local Signing" code-signing certificate in their login keychain. `build_app.py` now re-signs the Xcode output with that identity when exactly one exists, keeping hardened runtime and empty entitlements; otherwise it keeps the ad-hoc signature (CI and fresh checkouts). The policy check requires exactly that one authority with no team, or a pure ad-hoc signature, and the receipt records the mode. The local build's designated requirement is now the bundle identifier plus that certificate, which should keep privacy grants across rebuilds. The user re-granted Screen Recording for the newly signed app and reported that it works. After the later 0.3.1 rebuild the user reported that the app works, which indicates the grant persisted; this was not separately itemized. The certificate and key stay in the user's keychain and are not part of the repository. All 178 automated tests and the Release checks pass.

## M2 drag-out increment — November 12

Version 0.3.0 (6) rebuilds and passes all 169 automated tests plus Release bundle/signature checks, with no compiler warnings in app sources. Dragging a shelf thumbnail starts a native copy-only drag. Click thumbnails to select several; dragging a selected one carries the whole selection in shelf order. When the drag passes a 3-point threshold, the core's `beginFileDrag` writes each screenshot once to the app-owned temporary export directory (reused on repeated drags) and the drag carries a file URL plus the in-memory PNG data per item. If the mouse is released while exports are being prepared, no drag starts. Every prepared session is ended exactly once — on drop, cancellation or failure to start — which renews the 24-hour grace period; the shelf item is never removed by dragging. The shelf is held open during the drag and re-evaluates pointer/hover state afterwards. A drop does not mean a message was sent or an upload finished.

Export filenames are the core's generated identifiers (for example `<UUID>.png`), so destinations show that name. Readable names would require a reviewed core change and are tracked as follow-up work. After re-granting Screen Recording, the user reported that drag-out works. This is a user report without itemized per-destination results; which of Discord, Mail and Messages attached a file versus an inline image, multi-image drops, canceled/repeated drags and delayed drafts were not individually recorded.

## M2 region capture increment — November 12

Version 0.2.0 (5) rebuilds and passes all 156 automated tests plus Release bundle/signature checks. The user chose Control-Shift-4 and a custom overlay. The flow is: shortcut, menu item or camera button → islands hide → dimmed crosshair overlay on every display (Escape, right-click or a click without dragging cancels) → `SCScreenshotManager.captureImage(in:)` for the selected rectangle → in-memory PNG admitted to the shared `ShelfStore` (20 images / 128 MiB, no silent eviction) → islands return and the shelf on the pointer's display peeks for 3 seconds. Nothing is written to disk or the pasteboard by capture, and system screenshot preferences are untouched.

The shortcut uses the Carbon hot-key API, which receives only that combination and needs no Accessibility or Input Monitoring permission; the Settings switch unregisters it immediately, and Quit unregisters it. Screen Recording is requested only on the first capture; if already answered, the Screen Recording settings pane opens and nothing is changed there automatically. Because the app is ad-hoc signed, macOS may ask again after rebuilds. Copy is an explicit action that writes PNG data to the general pasteboard. Export cleanup now runs when the store opens at launch and every 30 minutes while running; an unexpected file stops cleanup without deleting anything and shows a message.

After running 0.2.0, the user reported that capture works on the MacBook. This is a user report, not an instrumented measurement; individual checks (focus retention, overlay absence, Copy, cancellation) were not itemized. Capture fidelity at Dell scaling remains untested. Dragging out of the shelf is the next increment, so there are still no exports to clean.
